# net.restconf.config

Writes one YANG data resource over RESTCONF (post, put, patch or delete), reporting whether it changed, with an optional pre-change backup.

Finds the device's RESTCONF root from its /.well-known/host-meta, read with no credential, or, when host-meta answers 404 or a redirect (never followed), as IOS XE answers it to anything but a valid login with a 302 to its WebUI's login page (404 there), takes the conventional /restconf for the first authenticated read to confirm; it reads its capabilities and YANG library as net.restconf.facts does (recording the same facts), and writes the resource path names with method: post creates content under path, put creates or replaces the resource at path, patch merges content into it, and delete removes it. A write to the conventional /restconf that nothing under it confirmed (neither the capabilities nor the YANG library answered) is refused before the document is sent. Parameter names are ansible.netcommon.restconf_config's own. The device is reached at its own origin with its own TLS (always verified, a pinned certificate included) and its own stored credential, following no redirect, and a refused credential is not sent again within the task. A request the device refuses with 409 Conflict, in-use, "Too many sessions." (IOS XE counts every RESTCONF request as a session until it expires) is sent again after a wait that starts at 2 seconds and doubles to at most 30, for up to 11 minutes a request and 15 minutes in all per task, and the task warns how many times requests were refused and how long it waited. IOS XE's answer suggests it opened no session for the refused try and applied nothing, which was measured for reads, never for writes, so a write sent again whose answer a first try having applied it would also explain (a post answered 409 data-exists or resource-denied, a delete answered 404, a put of a resource the read before did not find answered other than 201 Created) fails saying whether the first try applied it is not known, the resource read after where its path is known and no undo recorded. path is parsed, never passed on: each node is held to the YANG identifier grammar and each key decoded once and encoded again, so a key holding / or , stays inside its key and never addresses another resource. A module the device does not implement is refused before anything is sent, when its YANG library was read whole, and so is a datastore its library does not list. The resource is read before and after the write, in format, and the two compared with key order and white space set aside, so a run that leaves the resource as it found it reports no change: a put or patch of what is already there changes nothing, a delete of a resource that is not there sends nothing, and a post answered 409 Conflict (RFC 8040's resource-denied, or data-exists: the resource is there already, and post never replaces one) changes nothing and says so. A patch of a resource that is not there is refused before anything is sent. A rejected write comes back as the device's own ietf-restconf:errors, structured and masked. Every answer recorded (the backup, the diff and every error) is masked by value, the device's credential and every named secret the content resolved in each form it could be echoed in, and then by shape, every secret-named leaf and crypt-shaped value; the content itself is never recorded.

## Parameters

| Name | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `path` | `string` | yes | - | The resource to write, as RFC 8040 writes a data resource path: module:node/list=key1,key2/..., such as ietf-netconf-acm:nacm/groups/group=ops, under the root's /data, or under the datastore named. A key holding /, , or = must be percent-encoded (%2F, %2C, %3D); every key is decoded once and encoded again, and a path that does not parse is refused before anything is sent, as is a query, a fragment, an empty node or a dot segment. The first node names its module. For post, path is the parent the new resource is created under. |
| `content` | `string` | no | - | **Accepts `{{ secret.<name>.<field> }}`:** The document to write, in format: for post the resource to create under path, for put the resource at path whole, for patch what to merge into it. Required for those, refused with delete. JSON must parse; XML must be well-formed, with no DOCTYPE or other directive, and nest no deeper than 256 elements. A JSON string value or an XML leaf may name a stored secret, such as a pre-shared key, with a secret reference, {{ secret.<name>.<field> }} (pleiades add-secret): it is resolved just before the write, escaped as JSON string content or as XML text, and masked in everything the run reports; the content is never recorded. A reference outside a JSON string is refused. A document holding one holds no other template expression, so a per-device value and a secret go in separate tasks, and a value with whitespace, a control character or ? is refused. Content holding a masked placeholder (pleiades-masked-) is refused, since it would set each secret to the placeholder. |
| `method` | `string` | no | `post` | How to write: post (create under path; never replaces), put (create or replace the resource at path whole), patch (merge into the resource at path, which must exist), or delete (remove it). **Choices:** `post`, `put`, `patch`, `delete` (case ignored). |
| `format` | `string` | no | `json` | The encoding of content, and of the reads before and after: json (application/yang-data+json) or xml (application/yang-data+xml). **Choices:** `json`, `xml` (case ignored). |
| `datastore` | `string` | no | - | Write the NMDA datastore RFC 8527 addresses under the root's /ds/, ietf-datastores:running or ietf-datastores:startup, instead of the conventional /data. Refused before anything is sent unless the device's YANG library lists that datastore. candidate is not offered: RESTCONF has no commit, so an edit there would stay staged for the next commit by any client. **Choices:** `running`, `startup` (case ignored). |
| `backup` | `bool` | no | `false` | Record the resource as it was before the write under the backup stat, masked as every recorded answer is: empty when the resource was not there, and always for a post, which reads nothing before it writes (path is the parent, and the resource a post creates is not there yet). A document masking cannot vouch for fails the task before anything is written. |

| `tls.certificate.serial` | `string` | when the device was reached over TLS and presented one certificate, as a stat and a fact, unless its serial number is negative or longer than 40 hex digits | The certificate's serial number in lowercase hex, two digits a byte (00 for zero): the form openssl x509 -serial prints, lowercased. A serial longer than 40 hex digits, or a negative one, is left out, with a warning. |

## Undoing this

**Can be undone.** A run that changes something records the instruction that reverses it, as an `inverse` stat holding the method to call and the parameters to call it with, resolved from the state this run actually found. A run that changed nothing records no instruction, which is how it says that undoing it means doing nothing.

A run whose write the device answered as a create records net.restconf.config with method delete of the resource created, which is exact: a put answered 201 Created (RFC 8040 section 4.5), or a post answered 201 Created whose Location names one node directly under path (section 4.4.1). It is recorded as the 201 arrives, so it stands whatever happens after, the read after the write included. A put answered 204 No Content or 200 is a replace, whatever the read before found (a 404 can be access control hiding a resource that is there), and a post whose Location names anything else, or nothing, records no undo either; the run says why. A replace, a merge or a delete of a resource that was there records no undo: putting the earlier document back would keep it in the run's journal, which may hold secrets, so a rollback refuses such a task unless it is left (--leave) or the task's rollback: list says what to do; backup: true keeps the masked earlier document beside the run. A run that changed nothing records nothing.

`pleiades rollback` and the Controller's rollback route replay a recorded instruction. It is recorded during the forward run because the values an undo needs are gone once the change is applied.

## Examples

Create or replace an access-control group:

```yaml
- name: Make the ops group
  net.restconf.config:
    method: put
    path: ietf-netconf-acm:nacm/groups/group=ops
    content: '{"ietf-netconf-acm:group": [{"name": "ops", "user-name": ["alice"]}]}'
```

Remove a group whose name holds a slash:

```yaml
- name: Remove the ops/lab group
  net.restconf.config:
    method: delete
    path: ietf-netconf-acm:nacm/groups/group=ops%2Flab
```
