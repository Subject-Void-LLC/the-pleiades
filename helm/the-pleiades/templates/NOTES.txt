{{ .Release.Name }} is installed. Nobody can sign in yet: that is the next step.

1. Wait for the controller to be ready.

   kubectl rollout status -n {{ .Release.Namespace }} deploy/{{ include "the-pleiades.controller.fullname" . }}

   If it does not move, check for ImagePullBackOff first:

   kubectl get pods -n {{ .Release.Namespace }} -l app.kubernetes.io/instance={{ .Release.Name }}

   No Pleiades image is published to any registry. This release asks for
   {{ .Values.controller.image.repository }}:{{ .Values.controller.image.tag }} and {{ .Values.runner.image.repository }}:{{ .Values.runner.image.tag }},
   which are the names this repository's own build produces. Build and
   side-load them, or push them to your registry and reinstall with
   controller.image.repository and runner.image.repository pointed there.

2. Create the first administrator. Until this runs, there is no account.

   kubectl exec -it -n {{ .Release.Namespace }} deploy/{{ include "the-pleiades.controller.fullname" . }} -- \
     /app/controller bootstrap-admin --email you@example.com

   It prompts for a password with echo disabled, so it needs the -it. A
   password is never accepted as a flag value on any path, because a flag is
   visible in the process list to everyone else on the machine. In a script,
   pipe it instead:

   echo "$PASSWORD" | kubectl exec -i -n {{ .Release.Namespace }} deploy/{{ include "the-pleiades.controller.fullname" . }} -- \
     /app/controller bootstrap-admin --email you@example.com --password-stdin

3. Reach the UI.

{{- if eq .Values.controller.tls.mode "self-provisioned" }}

   Your browser will warn once. The controller generated its own certificate
   because none was configured: it encrypts the connection and does not
   authenticate the server, so nothing your clients already trust vouches for
   it. The certificate is reused across restarts, so the warning is a
   once-per-machine annoyance rather than a once-per-restart one.
{{- if or (gt (int .Values.controller.replicaCount) 1) .Values.controller.autoscaling.enabled }}

   NOTE, because this release runs more than one controller: they share one
   directory and converge on one certificate, but not instantly. If several
   replicas cold-start at the same moment and none of them finds a
   certificate, more than one may mint its own, and each keeps serving the one
   it read for the life of that process. They settle on a single certificate
   at their next restart, and nothing rewrites a certificate that can still be
   served, so it stays settled. Until then a browser may warn a second time
   after landing on a different pod. Nothing is unsafe about that: a
   self-signed certificate is only trusted by being handed to a client
   directly, so there was never a shared trust decision to break. If you need
   every replica to serve an identical certificate from the first second, that
   is what controller.tls.mode=secret is for.
{{- end }}

   In production, replace it. Either put a real certificate in a
   kubernetes.io/tls Secret:

     --set controller.tls.mode=secret --set controller.tls.secretName=<secret>

   or terminate TLS at your ingress and say so:

     --set controller.tls.mode=upstream
{{- end }}
{{- if not (or .Values.runbooks.configMapName .Values.runbooks.existingClaim) }}

WARNING: no runbook source is configured, so this release has nothing to run.
Both the controller and the runners are mounting the empty directory baked into
their images. Point runbooks.configMapName at a ConfigMap of runbook YAML, or
runbooks.existingClaim at a ReadWriteMany volume holding them, and reinstall.
Both workloads must see the same source: they resolve a dispatched runbook
independently, so two different directories means a job that launches on one
side and fails on the other.
{{- end }}
