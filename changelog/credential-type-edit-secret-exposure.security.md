A credential type edit could make every stored value of a secret input readable in plain text. Clearing the input's `secret` flag through `PATCH /credential-types/{id}` or `PUT /credential-types/{id}/inputs` did it in one request, and removing the input and adding it back as non-secret, through those routes or the web UI's Remove and Add input controls, did it in two; `GET /credentials/{id}` and the credential's edit form then showed the stored secret. The store now refuses clearing a secret flag, and deletes what every credential of the type stores for an input that is removed or added as non-secret; anything kept under an input added as secret reads back only as `$encrypted$`. Every credential create, update and input-source write, and every type edit, takes the type's row lock first (deleting a credential takes none, and a purge skips a credential deleted while it runs), and the API's PATCH routes and the web UI's forms apply their change to the record as it stands under that lock, so a credential write checked against a secret input is never committed under a plain one, and a change read before a type edit can no longer write back a reference the edit deleted, which would have resolved the secret into an input nothing masks. Key rotation, which writes outside the store, rewrites the same values and steps aside for a newer write. A read of a credential, and its resolution for a run, now reads the credential and its type in one read-only transaction: read in two statements, as they were, an edit committed between them that removed a secret input and added it back as non-secret showed the stored secret, and handed it to a run unmasked.
