A project now refuses a source URL that may carry a credential, for every type, on `POST /projects`, on `PATCH /projects/{id}` and in the web UI's project form, with a 400 telling you to give the project a credential instead, where manual and archive projects stored one unencrypted. The rule names what is allowed: a URL with no `@` (written, percent-encoded as `%40`, or a Unicode lookalike), no query and no fragment, or exactly one ssh login with no password (`ssh://git@host/org/repo`, `git+ssh://`, `ssh+git://`, or `git@host:org/repo`). Every other URL with an `@` is refused, git projects included, so `https://<token>@host/repo`, `git+https://<token>@host/repo`, `git://<token>@host/repo`, a password holding a `/`, an unparseable URL with a userinfo, and an `@` in a path (`https://host/org/repo@v1`) are refused, and so is any URL with a query or a fragment (`?ref=main` as much as `?sig=` or `#token=`), written, percent-encoded as `%3F` or `%23`, or as a Unicode lookalike, since a repository source needs neither. A token in the path cannot be told from a path and is not caught. A project that already holds such a URL, or gets one back from a backup taken before the rule, stays readable, with the credential shown as `redacted` or the URL withheld whole as `(withheld: the URL carries a credential)`, and an edit that leaves the URL as it is saves; a URL is checked when it is set or changed, and when the project becomes git, the first time it would be dialed. The same holds for the source policy: a git project stored with a source the policy now refuses can still be renamed, while changing its URL, or turning a manual project into a git one, is checked.
