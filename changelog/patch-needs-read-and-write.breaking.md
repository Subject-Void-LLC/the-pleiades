Every `PATCH` and `PUT` route, and every write-scoped `POST` that answers with the stored record it acts on (copying a template, syncing a project or cancelling its sync, attesting an organization or a team, testing a credential type, saving a template configuration), now needs the resource's read scope as well as its write scope, checked before the request body is read. Such a route answers with the stored record or judges its body against it, so a token holding a write scope alone could read any record by id (`PATCH {}`, or a copy), learn its organization by sending guesses, and probe its stored state through a refusal; it now gets one `403` for any id and any body. The web UI applies the same rule to its edit forms and record actions, where a session holding only a write scope used to open an edit form and see the stored record. No built-in role loses anything: an operator holds every read scope matching its write scopes, and an admin passes every check. A token minted with a write scope and not its read scope can no longer call these routes. The `OPTIONS` `Allow` header, the `_links` array and the UI's controls offer them only to a caller holding both.
