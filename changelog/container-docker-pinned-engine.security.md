`container.docker.run`, `stop` and `remove` now act only on the Docker engine onboarding pinned for the device: each asks `docker info` for the engine's identity first and refuses a different one, which the login's own docker configuration (`DOCKER_HOST`, a docker context) could otherwise point them at, as `container.docker.exec` already did. A device with no pinned engine is refused, naming `pleiades onboard`. `run`'s description now says what it always did: an existing container, stopped or running, is left as it is.
