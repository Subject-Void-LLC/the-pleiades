Commands that write the project's credential file at the same time no longer lose each other's entries. `add-credential`, `add-secret`, `add-registry-credential`, `add-database-connection`, `remove-credential`, `remove-secret`, `remove-database-connection`, an import that stores credentials and a run that binds an unbound credential each read `.pleiades/credentials.yaml`, changed one entry and renamed a new file into place with nothing held in between, so of twelve `add-credential` commands started together some were not stored while every command reported success. Each now holds an operating system lock on `.pleiades/credentials.lock` (flock on Linux, macOS and FreeBSD, LockFileEx on Windows) from before its read until its file is in place. The lock file is empty and is never removed; the system releases the lock when the command ends, a crash included, so nothing stale is left to clear. A command that waits 30 seconds for the lock stops with an error naming the lock file. Reading a credential takes no lock. Not covered: a `pleiades` older than this change takes no lock and still races with a new one, and a network filesystem that does not keep such locks between machines protects nothing.
