Routes that act on a record they read now need that record's read scope beside their action scope, checked before the request body is read, as the write routes already do: cancelling a job needs `job:read`; relaunching or rolling back a job needs `job:read` and `template:read`; launching or checking a template needs `template:read`; onboarding a device, granting or revoking one of its capabilities, and importing a kubeconfig need `inventory:read`; binding a template's credentials needs `template:read` beside `credential:read`, since it reads the template's kind first; and creating or editing a project needs `credential:read`, since it reads the credential it binds. A kubeconfig import's `inventory:write`, which its handler always required, is now declared on the route, so it appears in the document and the `Allow` header. Writing a schedule needs the same read scope its target's own launch route needs (`template:read` for a job template, `project:read` for a project), since a schedule is a second way to make the same run. Each of these answered with the stored record or a refusal judged against it, so a token holding only the action scope could read records it was never granted. No built-in role loses anything: operators and admins hold every one of these read scopes. A token minted with an action scope alone, such as a CI token holding only `runbook:execute`, now also needs the read scopes of what it acts on.
