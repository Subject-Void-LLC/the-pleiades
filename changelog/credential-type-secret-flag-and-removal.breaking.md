Editing a credential type now changes the credentials of that type. Removing an input deletes the value, the external reference and the input source every credential of the type holds for it, in the same transaction, and adding an input as non-secret deletes anything already stored under its id, where both used to leave the values in place, which also left those credentials refusing every later update; adding an input as secret keeps what is stored under it, shown only as `$encrypted$`. Clearing an input's `secret` flag is refused with a 400 naming the input, where it was accepted; remove the input and add it again instead. Any edit of a type, even of its description, deletes values an earlier removal left behind under an input it no longer declares, and an edit is refused with a 409 while a credential of the type cannot be decrypted with the Controller's key. Credential writes of one type, across every organization, now queue behind one another and behind an edit of the type. A managed type's release reconcile refuses to clear a shipped secret flag, empties an input it adds as non-secret and keeps what is stored under one it adds as secret, and never deletes what credentials hold for an input it does not ship, so rolling back and forward loses nothing for a secret input; a non-secret input's values written by the newer release are still deleted when it adds the input back, and the release ordinal on managed types that would stop that is not built. One credential of a managed type the Controller cannot decrypt stops that type's reconcile, for every organization, whenever a release adds a non-secret input to it, leaving the type as it was and logging `level=ERROR msg="failed to reconcile a managed credential type"` with the type's namespace and the credential that cannot be read. The kubeconfig import no longer rewrites a managed Kubernetes credential type it finds stored.
