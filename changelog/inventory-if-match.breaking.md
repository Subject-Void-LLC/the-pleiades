An inventory now has a version, moved by one on each committed update, and an `ETag` header (its version and a digest of what it holds, such as `"3.9f86d081884c7d659a2feaa0c55ad015"`) sent by `GET /inventories/{id}`, `POST /inventories` and `PATCH /inventories/{id}`. The digest means a write from a build that predates the version, still serving during a rolling upgrade or after a rollback, also changes the tag. Send the tag back exactly as read; a proxy that rewrites it as a weak tag (`W/`) breaks these requests. A `PATCH` that names `groups` or `devices` replaces that list whole, so it now needs an `If-Match` header holding the ETag the inventory was read with: one sent without it is refused with 428, and one whose `If-Match` does not hold the current ETag (another update committed since, or the header is `*`, a weak tag or a list) is refused with 412, on any `PATCH` that sends one. Before this, a client that read an inventory before someone removed a device from it, and then sent back the list it had read, put the device back, which on a shared inventory re-grants it to every team the inventory is shared with. A `PATCH` naming neither list needs no `If-Match`, and a missing inventory is still a 404 before either refusal. A client that patches a member list must read the inventory first and send its `ETag` back. The compatibility check reports nothing for this change, since the document can only say the header is optional: it is required only when the body names a list.
