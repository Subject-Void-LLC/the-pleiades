A project whose master key file is missing, or cannot be used, no longer gets a new key beside what the old one sealed: while `.pleiades/` holds a stored credential, a named secret, a registry account, a database connection, `seal.key` or stored facts, `add-credential`, `add-secret`, `add-registry-credential`, `add-database-connection`, `seal-key`, `import-kubeconfig`, `import-containerlab` and a run that reads a credential, masks a named secret or stores a fact each refuse, name what they found and the key to restore (`.pleiades/master.key` or `PLEIADES_MASTER_KEY`), and say to remove the files you accept losing if the key is truly gone. Before, a fact write already refused beside stored facts, but every other command made a new key and sealed what came next under it. A project holding nothing sealed still gets its key from its first command, reading ones included, and commands started together in a new project agree on one key. A set, well-formed `PLEIADES_MASTER_KEY` is still used as given, with nothing checking that it is the key the project was sealed under.
