Every command sent to a device over SSH now reaches it through `/bin/sh`, whatever the account's login shell is, so file, service, package, rollback, check, onboarding and async work behaves the same on a host whose account logs in to bash, zsh, tcsh or fish; before, a tcsh or fish login broke much of it, sometimes reporting success having done nothing. The login shell still starts and reads its startup files, so `PATH` and the environment are the account's own, but `sh` parses the command: an `ssh_exec` command written with bash-only syntax for a bash login now needs `exec.shell` with `executable: /bin/bash`, and a shell function or alias an rc file defines (nvm, conda `activate`, `module`) no longer reaches it. A `ForceCommand` or an `authorized_keys` `command=` wrapper that reads `SSH_ORIGINAL_COMMAND` now sees the `/bin/sh -c ...` line, and a command heavy in punctuation fits less text under the 128 KiB a line may hold; a command holding a NUL byte is refused. A network device's CLI, and a device onboarding found no POSIX shell on, still get each command as written; a `generic_ssh` host whose account logs in to fish and was onboarded before this release was recorded as having no POSIX shell, so run `pleiades onboard` on it again.
